# MuJoCo + MJX 能力补齐（引擎 + UI/UX + 模型注册表）

## 设计总览

补的是「接入能力与可见性」，不复刻引擎本体。三个交付面：

1. **`engines/mjx-adapter`** —— 纯 JAX 的 MJX 引擎适配器（真 MuJoCo 物理 + raw JAX PPO，端到端 vmap/jit），按现有 worker 文件协议接入，与 mjlab 适配器同构
2. **UI 原生融入** —— `physicsBackend`/`engine` 贯通到运行台账与详情（现被 `safeMetrics` 白名单丢弃），引擎选择复用现有算力资源机制
3. **mujoco-web 模型注册表** —— 部署方管理的受审 MJCF 白名单（不开放任意 XML，保持安全边界）

关键设计洞察（探索确认）：starter `GoalNavEnv` 的全部域随机化（motorGain/lag/noise/slip/dropout/bias）本来就是**指令级与观测级**的语义，与物理引擎无关。因此 MJX 环境的分工极干净：**MuJoCo/MJX 只负责机器人本体的真实动力学**（自由关节刚体 + 轮速执行器 + 轮-地摩擦接触 + 真积分），目标/障碍/奖励/终止/DR 全部 1:1 沿用 starter 语义。这保证了跨引擎质量门可比性（同任务、同指标、只有物理不同），`physicsBackend: "mjx"` 标注诚实。

## A. MJX 引擎适配器（核心交付）

**新文件 `engines/mjx-adapter/adapter.py`**（参照 mjlab 适配器协议骨架，~700 行）：

- **双后端诚实结构**：
  - jax+mujoco 可导入且带 task-pack → 真路径 `physicsBackend: "mjx"`
  - `RDK_MJX_ADAPTER_FORCE_MJX=0` 或无 pack → 回退 `physicsBackend: "starter-kinematic"`（同一个 JAX 学习器跑在 starter 的 GoalNavEnv 上）
  - jax 完全缺失 → 退出码 3 拒绝（与 mjlab 缺 rsl_rl 时行为一致），任务标 failed
- **MJX 环境 `MjxGoalNavEnv`**：
  - MJCF 场景从任务包生成：地板 + OriginBot 式差速底盘（freejoint、双轮 hinge + velocity 执行器、**碰撞几何用球体**保证落在 MJX 支持的接触类型内、后支撑万向球），timestep/decimation 取 contract 值
  - 批量步进：`mjx.put_model/put_data` + `jax.vmap` + `jax.jit`
  - 观测：8D `originbot-imu-odom-v1` / 42D `imu-gravity-v1` 两种布局都支持，从 MuJoCo qpos/轮速 + 里程计积分计算，噪声/丢帧/打滑语义与 starter 完全一致
  - 障碍/边界：解析圆碰撞判定（与 starter 相同语义，保证质量门跨引擎可比），障碍按 env 独立采样
  - 奖励/终止/课程学习：沿用任务包定义
- **纯 JAX PPO**：1:1 移植 starter 校准超参（entropy 0.002、lr 3e-4、clip 0.2、gamma 0.99、lam 0.95、4 epoch × 4 minibatch、[128,128] tanh MLP + 可学习 log_std），Adam 用 optax；param 用裸 pytree，无 flax/brax 依赖
- **ONNX 导出**：用已装的 `onnx` 包手工构图（Gemm/Tanh/Clip，opset 13，输入 `observation` 输出 `action`，动态 batch），契约与 starter 导出字节级同构
- **评测**：自写单环境 jitted rollout 产出与 starter **完全同形**的报告（包络 × Wilson CI × jsonl 行），复用 `load_starter_engine()` 的 `wilson_bounds`/`eval_domain_params`/`evaluate_quality_gate`；含未训练基线对比；`taskEvaluation` 嵌入 result（TS 侧 `validateTaskPackEvalForRelease` 可重算裁决）
- **result.json**：`artifact://mjx/...` 引用、`metrics.physicsBackend/engine`、`cuda` 按 `jax.devices()` 如实上报、`deployable: false`、退出码 2/3 语义与兄弟引擎一致
- 测试预算覆盖 env：`RDK_MJX_ENGINE_ITERATIONS/_ENVS/_STEPS`

**新文件 `engines/mjx-adapter/test_mjx_adapter.py`**（unittest，spec-load 模式，无 jax 时 SKIP）：文件协议冒烟、契约维度不匹配 → ValueError、ONNX 数值等价（jax 前向 vs onnxruntime，<1e-5）、DR 包络钉死复现性。

**实现第一步是 MJX 兼容性探针**：装好依赖后先写 20 行脚本验证 velocity 执行器、球-平面接触、implicitfast/Euler/RK4 在 `mujoco.mjx`（3.12）的支持情况，按结果定积分器与轮子几何，再写完整适配器——避免整写完才发现特性不支持。

## B. 本地环境（真路径本机可实测）

`/opt/homebrew/bin/python3.12 -m pip install --user jax mujoco optax onnx`（用户目录安装，可逆；遇公司代理 403 用 squid-proxy-403-fix 技能处理）。装完后 `verify:mjx-adapter` 在这台 Mac 的 CPU 上就能跑真 MJX 路径——不需要 GPU，这是 MJX 路径的演示故事。

## F. mujoco-web 模型注册表

- `services/mujoco-web/registry/`：部署方放受审 `<key>.json`（与 `ModelDefinition` 同形，含内联 MJCF）+ `README.md` 契约说明 + `.example` 样例文件（不加载）
- `models.py`：`load_registry_models()` 启动时读注册表 → 元数据形状校验 → `mujoco.MjModel.from_xml_string` 编译验证（无效条目 → 服务拒绝启动，fail-closed）→ 合并进 `MODEL_DEFINITIONS`，`ModelDefinition` 增加 `source: "builtin"|"registry"` 字段
- `/api/models` 返回 source；`app.py` 改动最小化（注册表合并点在 models.py，路由零改）
- 前端模型下拉自动出现新条目（零前端改动）
- 不新增玩具内置模型——注册表机制本身就是承诺的「部署方模型扩展能力」，随机加演示模型无产品价值
- `services/mujoco-web/README.md` 补 provisioning 段落

## H. 执行顺序与收尾

1. 装依赖（python3.12 --user）→ 2. MJX 兼容性探针 → 3. 适配器 + 测试 → 4. verify 脚本实跑（真路径 + 回退路径都绿）→ 5. TS metrics 贯通 + 测试 → 6. UI + 测试 → 7. 注册表 + verify → 8. 文档 → 9. 全量 `npm run verify` + `npm test` → 10. 浏览器 GUI 抽查新 chip/详情（web-gui-tester 技能，截图归档 gui-test-screenshots/）→ 11. **git-surgical-commit 分块提交**——工作区有用户未提交 WIP（dsh-runtime.ts、sim2real-routes.ts、local-runner.ts、board-*.py、agent-chat.js），只暂存本计划的 hunk，绝不扫入用户在途改动

## 明确不做（诚实边界）

- 不复刻 Isaac Lab/Playground 规模的万级 GPU 集群、可微分物理全家桶、模型生态
- 不开放任意 MJCF 上传（注册表仍是受审白名单）
- MJX 不做成平台硬依赖——无 jax 时 verify 脚本 SKIP，CI 与「无 GPU 可跑通」承诺不变
- starter-ppo / mjlab 适配器行为零改动（新增兄弟引擎，不动现有校准实现）
