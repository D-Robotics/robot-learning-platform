# 可扩展性与容量边界

这份文档把"现在能撑多少、什么时候会坏、坏了往哪走"写成可核对的边界，避免把 MVP 的存储模型误当成生产架构。

## 结论先行

当前存储层是**单进程、单实例、文件型**的：一个 JSON 台账（`<storage>/sim2real.json`）加每个 run 一个遥测分片（`<storage>/telemetry/<runId>.jsonl`）。它足以支撑单机演示、单团队内网部署和参考实现验收，**不支撑多副本、水平扩容或高并发写入**。

## 具体边界

| 边界 | 现状 | 影响 |
| --- | --- | --- |
| 多进程 / 多副本 | 写路径有**文件租约**，另有**只读副本模式**（见下） | 第二个**写者** fail-fast（503）；只读副本可以安全共存并横向扩读；仍不支持多写者 |
| 读取成本 | 解析结果带 `(size, mtimeMs)` 校验的进程内缓存；命中时只做一次 `fs.stat`。仅首次读或文件被原子替换后解析整个台账 | 台账越大，**冷读**越慢；高频读由缓存兜住（只读副本因此受益）。缓存刻意不做"路径级"命中，避免备份/恢复后读到旧值 |
| 台账配额 | 100 自定义模型 / 10,000 run / 200 部署计划 / 768 MiB | 到顶 fail-closed，返回 `507`，不静默淘汰 |
| 遥测容量 | 每 run 最多 `SIM2REAL_TELEMETRY_RECORD_CAP = 100_000` 条记录，append-only | 到顶 fail-closed；无自动淘汰时需人工清理 |
| 遥测读取 | 小 `limit` 的列表请求只解析需要的头部记录（有界读） | 已优化；`/replay`、`/evaluate` 仍需全量，这是刻意设计 |
| 蓝绿 / 滚动发布 | 无共享存储与租约协调 | 不成立 |

## 支持的部署形态

| 形态 | 是否支持 | 说明 |
| --- | --- | --- |
| 单实例读写 | ✅ | 默认形态 |
| **1 写 + N 只读副本** | ✅ | 写实例正常；只读副本设 `RDK_SIM2REAL_STORAGE_READ_ONLY=1`，共享同一 `RDK_SIM2REAL_STORAGE_DIR`。读是原子的（台账 tmp+rename），副本永不写、也不碰租约文件 |
| 多写者 | ❌ | 第二个写者会 fail-fast；要真多写者必须换 PostgreSQL 等共享事务存储 |
| 蓝绿 / 滚动发布 | ❌ | 需要共享存储与租约交接，当前不具备 |

## 已经做的缓解

1. **写者租约**（`<storage>/writer-lease.json`）：写台账前先获取/续租。同主机看 pid 存活（`EPERM` 视为存活），跨主机或 pid 不可判定时看 `heartbeatAt` 新鲜度（默认 300s，`RDK_SIM2REAL_STORAGE_LEASE_STALE_SECONDS` 可调，10..86400）。判定为冲突时抛 `sim2real_storage_writer_conflict`，HTTP 层映射为 **503 + `retryable: false`**，并给出"换 `RDK_SIM2REAL_STORAGE_DIR` 或确认旧进程已退出"的可执行建议。租约文件损坏/版本未知/读失败一律 **fail-closed**（当作冲突），绝不当作"无租约"放行。`RDK_SIM2REAL_STORAGE_LEASE=0` 可关闭（仅排障用，关闭后无任何跨进程保护）。
   - 已知局限：跨主机共享挂载时只能靠心跳新鲜度，因此无法区分"另一台机器上的活写者"与"刚崩溃的写者"；硬杀进程留下的租约由 pid 存活/心跳过期兜底。
2. **只读副本模式**（`RDK_SIM2REAL_STORAGE_READ_ONLY=1`）：所有写路径抛 `sim2real_storage_read_only` 并 fail-closed；不获取/续租/释放租约，因此既不会破坏写者，也不会因为写者持有租约而启动失败；读取与既有台账完全正常。健康检查会如实标出 `storage.readOnly`，且**不**把它算作降级。
3. **有界读**：`GET /runs/:id/telemetry?limit=N`（N 远小于上限）只从头解析到第 N 条需要记录即停止，不再解析整个分片。`/replay` 与 `/evaluate` 明确传上限，保持全量语义——评测不允许静默截断。
4. **遥测保留**：`RDK_SIM2REAL_TELEMETRY_RETENTION_DAYS`（默认 `0` = 关闭）。设为正整数时，写入路径会同时淘汰分片中过期记录**和**台账里对应的索引行，保证两侧一致（不会出现孤儿索引或孤儿分片）。非法值（非数字、≤0、>3650）一律按 `0` 处理。
5. **遥测与台账分离**：分片先落盘、台账后提交；崩溃只会留下不可见的孤儿行，而不会留下悬空索引。
6. **台账读缓存**：解析结果按 `(size, mtimeMs)` 校验复用，运维在备份/恢复时原子替换台账也能立刻失效缓存（不会读旧值、更不会用旧值覆盖新文件）。

## 扩容路径（按投入排序）

1. **换存储**：台账迁移到 PostgreSQL（行级锁 / 事务），遥测迁移到对象存储或时序库，保留现有 `Sim2RealStore` 接口形状；届时文件租约由数据库事务取代。
2. **加租约（已完成文件层版本）**：多实例部署前必须确认 `RDK_SIM2REAL_STORAGE_LEASE` 处于默认开启状态；关闭它等于放弃跨进程保护。
3. **遥测 TTL**：在正式环境显式设置保留天数，并按"每天样本量 × 天数"核算磁盘。
4. **读缓存**：台账已有 `(size, mtimeMs)` 校验的解析缓存；如果要进一步降冷读成本，应按 run 分片或引入 LRU，而不是简单延长缓存有效期（那会牺牲备份/恢复的正确性）。

## 容量估算方法

单条遥测样本的近似字节数 × 采样频率 × 会话时长 = 每会话分片大小；再乘并发的板端会话数，就是峰值写入速率。台账大小主要随 run 数量线性增长（索引行不带 samples）。做容量规划时请用真实录制的分片，不要用合成样例外推。
