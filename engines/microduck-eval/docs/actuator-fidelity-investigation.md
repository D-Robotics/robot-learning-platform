# 执行器保真度调查（2026-09-16，第 2 轮）

**问题**：标定后的评测装置能让零动作基线站住，却让一个真训练策略每次都摔。
在判定"策略不行"之前，必须先判定"装置行不行"。这一页记录查过什么、排除了什么。

| 项 | 值 |

## 2. 逐项排除（都在同一信封、同一初始态下做）

| 候选原因 | 做法 | 结果 | 判定 |

| 动作缩放 | 上游 `joint_pos_action.scale = 1.0` | 本机同 1.0 | 排除 |

## 3. 剩下的解释：策略训练量不足

上游 README 的口径是 **4096 环境、1–2 小时**才能得到可用步态；被评这个产物只有
**256 环境 × 1500 轮（≈ 9.2 M 步）**，约为推荐量的一小部分。它的表现与"半成品策略"完全吻合：
已经在朝正确方向走（前进是基线的 45 倍、速度误差改善 46%），但还没学会不摔。

因此本轮不做结论、只做**判据**：装置是否可用，要等一个足量训练的产物来回答。
已提交 `walk`，4096 环境 × 6000 轮（run `50975591-cebc-41d2-bac0-bd4946ee1d21`）。

## 4. 这一轮沉淀成机制的东西

`harnessQualification` 现在有第二条判据，且只在**被评对象标记为可信**时生效
（`--trusted-policy`）：

```
零动作基线站住，但被评策略每个 episode 都摔  =>
harnessQualification.passed = false
qualityGate 强制 FAIL，理由写明"不能判定学习策略，成功率无意义"
```

这条规则的价值是**双刃**：装置不合格时，它既不许认证一个好策略，也不许判死一个坏策略。
未训练的冒烟产物不带 `--trusted-policy`，因此不会被误判成装置问题。

## 5. 仍未解释的可能性（留给下一轮）

1. 4096×6000 产物在本机复评仍全摔 ⇒ 装置确实缺了某个物理项，届时需要一个**逐步轨迹对照**：
   在上游自己的机器上跑同一策略并 dump `obs/action/qpos/qvel`，与本机逐帧比。
2. 4096×6000 产物在本机能站能走 ⇒ 装置可用，先前只是策略不足；此时应把"足量训练"写进
   评测报告的前置条件（`policyProvenance` 已记录来历）。
3. 上游 BAM 的 `kp_fw` 语义若与我们的读法不同，`--actuator-model bam` 的缩放要重定；
   在拿到 2 的结论之前不投入这条。

## 6. 恢复接入所需（当前阻塞项）

本机的工作台进程（18102）与 GPU SSH 隧道（19092）在 13:02 一起消失。重跑需要：

* **GPU 机器的 ssh 目标**（`user@host` 与端口）——隧道目标没有落在任何本地文件里
  （台账只存 `runnerUrl` 和 token），需要由人提供一次；
* 然后 `ssh -N -L 19092:127.0.0.1:19092 <user>@<host>`（见
  `engines/microduck-rl-adapter/README.md` §3），并在工作台「训练 → 我的 GPU 训练资源」
  重新「测试连接」续上 600 秒健康租约；
* 训练进程在远端继续，产物（`policy.onnx` + checkpoint）留在远端 worker 的任务目录，
  只要 worker 进程不被重启就还在；恢复后 `GET /api/v1/duck/runs/<id>/policy.onnx` 即可取回。

**注意 6000 轮的预算**：按实测 0.85 轮/秒，6000 轮约需 2 小时；若想更快拿到判据，
停掉后改提 4096 环境 × 1500 轮（约 30 分钟）即可——曲线显示 113 轮已到 76 分，
1500 轮远在收敛区内。
