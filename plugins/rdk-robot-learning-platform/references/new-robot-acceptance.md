# 新机器人接入与验收（Qoder + RDK 插件）

## 从哪一步开始

Qoder 加载插件后，对话：“接入这台新机器人，先不运动，检查接口与标定，建立逐机验收记录，缺现场信息时告诉我。”
新学员先调用 `rdk_classroom_guide({scenario:"new-robot",answers})`，从上下文提取已有答案，每次只问一个中文待补问题。阶段标准需要时再调用 `rdk_robot_onboarding_guide`（默认简短，detail=full才展开原文），按实际授权保存模板到项目私有证据目录；用 `rdk_robot_acceptance_assess` 做字段覆盖审查。缺身份或摘要时返回needs-input、中文missingInputs及一个nextQuestion，所有阶段仍阻塞；不能填假摘要。技术摘要由助手核对，学员不手写。检查器不保存或签署记录，不读取收据原文，不提供运动许可，`documented` 只表示提交字段满足约定。
账号登录、安装与实际宿主验证见 [Qoder 安装](qoder-first-run.md)。地址、凭据和本机路径只留在私有配置，分享前脱敏。

## 三类可复用内容

- 通用流程：证据绑定、时效、看门狗、日志预算、停止/恢复、静止与抗扰分开评价。
- 机型适配：观测和动作维度/顺序/单位、SDK、串口协议、实时环、急停。新机型需要实现和验证代码；不能仅填一个配置就假定可运行。现有差速车适配器不代表兼容关节机器人。
- 逐机标定：关节身份与方向、零偏、安装轴、IMU变换、机械限位、供电。不能照抄 OriginMan 样机的ID、中心或符号。

## 阶段与证据

|阶段|先完成什么|留什么证据|
|---|---|---|
|interface|查官方协议、已安装SDK源码；确认状态码、阻塞和重读语义|来源链接/源码摘要、是否明确查询频率、完整请求时序；官方未给上限则写未知并实测，波特率不是查询频率|
|inventory|确认真实设备、供电模式、单一I/O持有者、温度/电压可读|带接收时间、命令/关节ID/状态的原始回包；不import会发动作的模块|
|calibration|官方站姿与零偏先只读，补逐机方向/轴向/机械限位|逐关节映射、单位与变换、现场观察；未知方向不猜，不叠加已保存零偏|
|parity|固定原模型、归一化、参考轨迹、适配器与运行时|原字节摘要、主机/板端相同输入输出及容差；合成输入不叫真实遥测|
|shadow|完整真实传感→估计→推理→目标计算，零致动|全周期延迟分布、数据年龄、丢读/过期、日志和恢复/看门狗测试；平均推理耗时不够|
|static|已实现执行器、门禁和现场保护，有限短试后延长|计划与实际发送、回读、开始/趋势/结束温度、操作者确认无人支撑；静止不证明抗扰|
|recovery|传统反馈与RL相同限制、相同测试方法|两组原始日志、恢复指标与现场观察；手动轻触不报告精确牛顿力|
|endurance|明确时长和停止条件，验证热与通信长期趋势|不中断计数、所有停止原因、热趋势、保护恢复；一次20秒稳定不代表根因已解|

模板的五个绑定字段必须固定：robotId、adapterSha256、calibrationSha256、policySha256、runtimeSha256。adapter摘要覆盖接口/单位/观测动作契约；runtime摘要应来自规范化文件清单，覆盖控制代码、频率、限幅、变化率、估计器、超时、温度门限和依赖身份。不得只hash一个无关脚本。每份收据绑定同样身份，有 observedAt、expiresAt 和原始收据SHA-256。有效期由验收方依据变更与设备状态设定，不能延长有效期替代复测。机器、标定、权重或运行时改变就重做相关证据。此版本保守地要求各阶段完整身份一致。

原始收据还应记录 run/session、操作者观察、开始/结束状态、实际测量、标准来源、异常与恢复；模板facts是审查索引，不是原始证据。未执行使用null/不填，失败使用false；不从历史日志自动填true。所有阶段覆盖仍不能自动修改制品 hardwareEligible。

## 通信与温升：先区分软件与硬件

1. 上电前准备好脚本和提示。核对原始协议和官方SDK的查询/导入副作用、串口持有者、重读次数与真实超时；同一串口只留一个所有者。不能把SDK默认几十次重读直接放入实时周期。
2. 用有界、查询白名单的诊断；按同一次上电记录查询顺序、间隔、总请求量及供电/承重。有效CRC的负状态与完全0字节是不同故障，分别保留，不能转成0值。
3. 请求期限在取队列前后检查；接收时间不是传感器采样时间。用完整循环实测查询频率，不承诺通用Hz。改频率/估计器后同配置仿真与影子复验。
4. 低频诊断等待要在调用线程分段维持租约和取消检查；后台心跳不能替卡死控制环续命。日志有界缓冲，避免每帧全量重写/同步刷盘；强杀可能丢缓冲，另留恢复收据。
5. 固定读取温度、电压和状态，分别比较不承重/承重、纯电池/充电；具体门限来自机型规范和本次工程方案，不复制案例温度。持续升温、负状态、全链路无字节均停止下一阶段。温度门限不是通过修改阈值来“修复”。
6. 保留软件版本、原始回包、温度趋势、原进程身份、停止原因和恢复结果。只恢复同身份原进程；重启服务可能触发开机动作。需要断电/查接头时明确告知操作者，不自动反复上电。软件修复要有修复前失败的反例及修复后测试；若故障仍存在，保留未解决状态再移交硬件隔离。

## 本次经验的结论边界

OriginMan 曾完成旧策略30秒静止，新候选完成30秒真实传感影子和3秒实体静止，操作者确认自行站立。新候选实际目标与去掉学习残差的单步计算有差异，说明策略参与，不证明闭环优势。抗扰对照未完成。通信负状态与温升仍未根治；已修复诊断心跳、日志开销和过期队列接受等软件缺陷，不能据此宣布硬件健康。新候选的独立摘要见 [历史证据](originman-candidate-evidence.json)，详见 [OriginMan 专项](originman-onboarding.md)。

## 停止与恢复

异常回包、超时、温升或运动结果未知时停止后续动作，记录本轮 stopped/failed，不写 completed。故障时不从未知姿态自动回中心。软件停止投递成功也不保证物理停止，回读和现场确认分别记录。先完成离线修复和零致动检查，恢复实体测试时再确认当前现场；已有授权不反复索取，但过时现场状态不能当作当前状态。
